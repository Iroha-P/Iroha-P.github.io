01 / SCENARIO & MY ROLE

当平台要快速聚合几十款 AI 工具，痛点不在单点模型而在「规模化治理」

电商内容团队每天需要高频调用不同模态的生成能力：商品图换背景、短视频生成（如 Seedance 2.0、Vidu）、扣子（Coze）工作流以及智能体对话。如果每接入一个新模型就各自写一套前后端：

  • C 端用户心智割裂：每个工具的输入框、进度提示、历史找回位置都不一样，运营切换工具时学习成本极高，刷新页面后生成的素材容易丢失。
  • 开发供给效率受限：不同开发者写的子工具目录结构、端口分配、密钥配置各自为政，联调和部署经常撞端口或漏配依赖。
  • 成本与故障成黑盒：异步视频/图片生成耗时长，上游模型 API（vtrix / Coze）返回计费字段不统一，管理后台难以定位「具体是哪个用户、在哪个工具、调哪个模型烧掉了预算或频繁报错」。

我在实习期间担任大模型应用开发工程师，一方面负责部分工具的开发与日常运维，另一方面将平台的架构约束、前端交互规范、消费统计机制与部署检查项沉淀为 880 行结构化的《新工具接入提示词》。上方保留的 SeaMe 官方市集 ↗ 为公开业务入口，本页则从产品策划与平台治理视角复盘其中的设计判断。

02 / PROMPT-AS-SPEC

用「可执行接入 Prompt + 7 项清单」替代传统 PRD，让新工具生成即合规

传统平台靠文档约束开发者，但文档越长越没人逐条核对。我们的做法是把平台规范产品化为一份可直接发给 AI 编程助手的 Prompt 模板：

填写 5 个需求字段（工具名 / 英文 Prefix / 6 大分类 / API 类型 / 功能描述） → 生成标准单文件前端 + 12 端点 FastAPI 后端 → 按 7 项清单完成 4 处平台注册与依赖校验

在这套规范下，任何新接入的工具都默认满足以下统一契约：

  • 统一分类与目录契约：按 image-tools / video-tools / agent-tools / 3d-tools / data-tools / game-tools 归类，三位数递增编号（如 028_xxx），固定包含 app.py、config.json、requirements.txt、start.bat 与单文件 templates/index.html。
  • 12 个标准 API 端点：强制实现 /api/create-task、/api/generate、/api/task-progress/{client_id}/{task_id}/{run_id}、/api/active-tasks、/api/history、/api/load-session、DELETE /api/clear-output 及在线人数 WebSocket /ws/online。
  • 中心化密钥继承：子工具本地 config.json 密钥留空，启动时通过 _load_central_keys() 自动从中央 web/config.json 继承 vtrix_api_key 与 coze_pat，换 Key 时无需修改几十个子工具。
03 / C-END ASYNC UX & SELF-HEALING

把漫长的异步等待和意外中断，设计成用户可感知、可恢复的闭环

图片和视频生成往往需要数十秒到数分钟。为了不让用户面对「假死转圈」，规范从前端布局到后端生命周期做了三层保障：

  • 统一三步式工作台骨架：所有工具共用 Sticky 渐变顶栏（展示实时在线人数绿色脉冲圆点、历史记录、密码保护的设置弹窗、返回首页）和编号三面板（① 输入表单 → ② 生成按钮与 2 秒间隔进度轮询 → ③ 结果网格与 Lightbox 灯箱预览）。
  • 无需重登的跨刷新会话恢复：前端在 localStorage 生成持久化 client_id 指纹，配合后端 SessionStore（12 小时 TTL、上限 200 会话）与 output/工具名/client_id/task_id/results/run_id/R_001.png 标准落盘路径，用户关掉网页再打开也能从「历史记录」一键恢复会话与产物。
  • 服务重启自愈与并发保护：后端通过 _TrackedSemaphore(5) 控制并发并持久化 _failures.json / _successes.json；同时注册 @app.on_event("startup") 启动清理钩子——一旦服务重启，自动扫描所有残留的 status == "running" 任务并改写为 error（"服务重启，任务中断"），彻底杜绝前端无限轮询死等。
04 / TRANSPARENT PROXY & TWO-PHASE BILLING

开发者零感知的透明代理计费：两阶段日志 + 四级费用兜底

多工具平台最核心的运营诉求是算清每一分模型调用成本归属于哪个用户、哪个工具、哪个模型。如果要求每个工具开发者手写计费埋点，不仅容易漏记，独立子插件进程也会丢失上下文。平台通过底层拦截实现了透明治理：

工具调用 cloud.vtrix.ai → httpx 猴子补丁透明拦截 → 本地 /vtrix-proxy/ 转发并提取 ContextVar (user_id + tool_prefix) → Phase 1 记 Pending 预估 → Phase 2 终态覆盖实付 USD → 写入 SQLite VtrixUsageLog

  • 双模式归因覆盖（统一入口 + 独立子插件）：通过 main.py 挂载的工具自动享受 httpx 猴子补丁拦截；对于带有独立子进程的工具（例如视频复刻工具下的 021_shipinfuke_v2/plug-in/seedance/），规范提供三行 vtrix_hook.install(tool_prefix=..., app=app) 挂载 UserIdMiddleware，确保子进程同样能完成用户级归因。
  • 为什么强制用 asyncio.create_task() 而禁用 threading.Thread：平台通过 Python contextvars.ContextVar 在请求链路中传递 user_id 和 tool_prefix。asyncio.create_task() 会自动继承当前协程的 ContextVar，而新建线程会导致 user_id 丢失变成匿名调用——把这一底层约束写进接入 Prompt，从源头保证了账单归因准确率。
  • 异步任务的两阶段记录（Two-Phase Logging）：针对耗时的视频/图片生成，Phase 1（POST 提交任务）立即写入一条 status=pending 的预估费用日志；Phase 2（GET 轮询完成/失败）再用实际费用覆盖预估值并更新终态为 success / error，避免长任务执行期间账单缺失。
  • 四级费用计算兜底：代理按优先级提取费用：① API 响应中的 usage.cost（实际 USD）→ ② 顶层 cost 字段 → ③ credits 积分换算（1 积分 = 1 USD）→ ④ 上游未返回费用时按模型规则兜底预估（如视频模型按秒计价：Seedance $0.15/s、Vidu $0.05/s；图片模型按次计价：Spark Dream $0.02/次）。

中断与故障反馈 进程重启后旧任务保持 running，前端无限轮询 Startup 自动扫描 _meta.json 将残留 running 改写为中断错误，区分输入错误与服务异常 把失败恢复当成核心体验，给用户明确的下一步动作（改参数或重试），减少无效等待

06 / ACCEPTANCE CHECKLIST & METRICS

7 项上线验收清单与两层业务评估指标

在日常开发与运维中，每一款新工具上线前必须通过 7 项工程与体验检查清单：

  • ① 目录与单文件前端合规：xx-tools/NNN_工具名/ 下 5 项标准文件齐全，前端配色、三步面板、2s 轮询与历史会话恢复正常工作。
  • ② 四处平台注册同步：main.py（TOOL_MOUNTS）、web/app.py（TOOLS 门户卡片）、requirements/services_config.py（端口自 8165+ 递增分配）、all_requirements.txt 与 install.bat 检测验证阶段全部对齐。
  • ③ 异常自愈与计费归因核验：验证失败计数（/api/active-tasks）、重启残留清理、磁盘清理端点以及后台 VtrixUsageLog 的用户与工具费用记录准确无误。

从「能跑通」到「有业务价值」的评估延伸（建议指标边界）：在工程稳定性（任务生成成功率、平均排队与响应耗时）之外，面向电商内容业务建议进一步跟踪两项核心价值指标——用户确认首份可用素材耗时（Time-to-First-Usable-Asset）与每份被采纳素材消耗的真实模型成本（Cost-per-Adopted-Asset）。生成成功率衡量系统健壮性，单份可用素材耗时与成本则共同衡量 AI 工具的真实交付 ROI。

口径说明：上文架构机制、接口契约、两阶段计费与四级兜底规则均整理自本人参与维护的 SeaMe 平台接入规范；「首份可用素材耗时」与「单份可用素材成本」为产品复盘提出的评估框架，不代表已公开披露的商业营收数据。
