01 / USER PROBLEM & JOURNEY

通用聊天模型给得出「八股题」，但帮不了候选人应对基于自身经历的深挖追问

求职者在准备目标岗位（如 AI 产品经理或大模型研发）时，核心痛点不是缺少泛化题库，而是不知道自己手头的项目材料能支撑哪些岗位要求、哪些地方会被面试官追问穿帮。如果直接让通用大模型润色简历或出题，极易出现「顺着岗位 JD 替候选人编造未做过的职责和量化指标」的问题。

我们将求职准备收束为一条受证据约束的五步连续状态流：

01 岗位方向诊断 → 02 经历证据匹配（标记已支撑 / 待补） → 03 针对性能力补强 → 04 单轮聚焦面试追问训练 → 05 投递与答题复盘

02 / MY AGENT ORCHESTRATION

个人贡献：负责除评测外的全部 Agent 状态流与工具边界编排

在三人团队中，我担任项目负责人，统筹整体方案与答辩演示，并独立完成除评测模块外的整个 Agent 编排设计。为了解决单次 Prompt 长对话容易丢失岗位目标、越界扩写和乱调工具的问题，我在编排层做了三项结构化设计：

  • 切分「LLM 生成」与「确定性规则工具」边界：大模型专注于意图理解、岗位—经历差距分析、追问组织与自然语言反馈；而评分计算、训练计划生成与落库、确认状态校验全部收归确定性规则工具执行，防止模型口头承诺修改却未落盘。
  • 强制证据对齐与「待补」标记（Anti-Hallucination）：在经历匹配节点加入证据核验约束——凡是候选人材料中没有原文支撑的能力项或量化结果，Agent 必须显式标记为「待补证据」并转为追问问题（例如追问本人具体如何执行），严禁替用户凭空捏造职责或数据。
  • 单轮单题节律与人工确认门控（Human-in-the-Loop）：模拟面试节点强制每次只抛出一道核心追问，根据候选人回答深度决定继续深挖还是切换下一题；当涉及更新求职计划或写入外部状态时，状态图触发中断（interrupt）等待用户显式确认后再继续执行。
03 / PRODUCT TRADEOFFS

先用文本 MVP 跑通「证据—追问—反馈」闭环，再规划多模态输入

竞赛初期团队曾讨论是否一上来就接入实时语音面试和简历排版渲染。我做出的产品取舍是第一阶段坚定聚焦文本 MVP：

  • 为什么先砍掉外围多模态包装：求职训练的核心价值在于「追问是否切中经历薄弱点、反馈是否诚实可操作」。如果文本链路上的方向漂移和经历扩写没解决，加上语音只会让错误更难排查。
  • 与 GradLoop 底座的复用关系：底层直接复用自研 GradLoop 底座 → 的 BM25 / 混合检索、SQLite 跨请求状态与 SSE 流式反馈，将团队精力集中在求职领域的 Agent 路由、Prompt 约束与回归验证上。
04 / REGRESSION EVALUATION

用 20 条固定合成用例复测 4 类策略 Badcase

为了避免「改好一个 Prompt 又弄坏另一个场景」，团队构建了 20 条固定合成回归用例，专门针对 Agent 编排中最容易出现的 4 类策略退化进行复测：

CareerPilot 回归评测重点监控的 4 类 Agent 策略问题与判定口径
Badcase 类型 典型合成输入场景 修改前的失败表现 编排优化与复测通过口径
1. 经历无中生有扩写 输入仅提供「协助整理测试记录」，目标岗位要求独立负责评测体系 模型自动脑补「主导构建自动化评测平台，提升效率 40%」 禁止编造职责与百分比；输出必须将该项标为「待补」，并追问本人「如何记录、按什么维度归类问题」
2. 岗位方向漂移 多轮对话后候选人聊起无关技术细节 Agent 顺着闲聊偏离目标岗位核心考察维度 状态节点持续注入目标岗位 Anchor，偏航后在下一轮追问中拉回待验证的能力项
3. 单轮抛出多道题 进入模拟面试阶段，候选人回答简短 模型一次连问 3～4 个大问题，候选人无法逐一作答 输出后处理与 Prompt 双重约束单轮仅保留 1 个主追问，追问完再进入下一节点
4. 绕过人工确认 用户模糊表达「差不多可以改计划了」 Agent 未经确认直接覆盖原有训练计划 写操作前置确认校验规则，未收到明确确认指令前保持待确认挂起状态

评测边界说明：上述 20 条用例为竞赛阶段固定合成输入与策略复测记录，用于验证 Agent 编排与 Prompt 约束的回归稳定性，不代表大样本真实求职者就业转化率实验。
